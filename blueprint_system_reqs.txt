11. Data Strategy
11.1 Data philosophy
The main development dataset will be generated, controlled and versioned by the project. This avoids dependence on purchased datasets, protects privacy and - most importantly - gives the team ground truth for every scenario.
11.2 Business simulator
business_simulator/
  customers
  products
  orders
  payments
  shipments
  tickets
  invoices
  vendors
  events
  policies
The simulator should generate normal and intentionally problematic records. A fixed seed must allow deterministic regeneration.
11.3 Initial data scale
Start with a small deterministic dataset suitable for debugging (for example 100-500 customers and a few thousand transactions).
Scale to 10,000+ customers and 25,000+ orders for stress/evaluation runs only after correctness is established.
Keep small fixtures for unit/integration tests so the test suite remains fast.
11.4 Ground-truth records
For each evaluation scenario, store the expected intent, entities, tools, policy, approval requirement, allowed action and expected final state. These records become the reference against which the agent is evaluated.

13. Agent Design
13.1 Agent responsibilities
Interpret the incoming request/event.
Identify required context.
Plan a safe sequence of tools.
Generate structured action proposals.
Use retrieved knowledge and business state.
Escalate when ambiguity, risk or policy requires it.
13.2 Agent must not control
Final authorization of sensitive actions.
Database truth for business state.
Permission boundaries.
Secret retrieval.
Money movement without deterministic approval controls.
13.3 Structured action contract
{
  "action": "refund_order",
  "order_id": "ORD-8472",
  "amount": 72000,
  "reason": "customer_requested_cancellation",
  "risk": "high",
  "requires_approval": true
}
The application validates this object, checks policy and authorization, then decides whether any tool can actually execute it.
